# RLE-NOC 项目初步分析报告

## 一、对项目的初步认识

这次主要通过阅读项目说明、部分 Python 程序和已有的运行记录，了解 RLE-NOC 的基本用途，并根据自己的理解进行了排队、选路和参数对照练习。刚开始看到项目里有很多文件，感觉内容比较复杂，但从几个主要脚本入手后，可以大致理解它要解决的问题：当芯片内部有很多数据需要传输时，怎样选择路线，才能减少等待时间。

芯片内部有多个计算核心，它们之间需要交换数据。这里的“片上网络”，可以简单理解为连接这些核心的道路。数据从一个位置送到另一个位置，需要经过一些中间节点。如果同时传输的数据太多，某些地方就可能出现排队，类似道路上的堵车。

这个项目希望利用强化学习来选择合适的路线规则。我的初步理解是，让程序多次尝试不同选择，再根据传输效果积累经验。

## 二、项目的基本思路

传统方法可以按照事先规定的规则传输数据，实现起来比较直接。但网络中的数据量会变化，同一种规则不一定在所有情况下都合适。

项目提供了三种路线规则，程序会从中选择一种，然后通过模拟实验观察效果。代码中出现的 XY、Random oblivious 和 West-first，就是这些规则的名称。初次接触时，可以先把它们理解为三种不同的“走路方式”，暂时不必深入每种规则的具体实现。

整个过程可以概括为：

1. 设置当前要发送多少数据。
2. 选择一种路线规则。
3. 运行模拟，记录数据传输的平均耗时。
4. 根据结果调整记录，为之后的选择提供参考。

在当前主要脚本中，平均耗时越小，得到的评价就越好。项目不是让程序随意创造一条新路线，而是在已有的几种规则中进行选择。

## 三、主要文件的作用

从初步阅读来看，理解项目不需要一开始就看完所有代码，可以先关注下面几个文件。

| 文件或目录 | 我的理解 |
| --- | --- |
| `README.md` | 介绍研究背景、论文信息和基本运行方式 |
| `interconnect-routing-gym/example/icn_gym.py` | 把学习程序与模拟工具连接起来，负责启动模拟和整理结果 |
| `interconnect-routing-gym/example/rl_QLearning_example.py` | 使用 Q-learning 方法，反复尝试并记录选择效果 |
| `interconnect-routing-gym/example/extract_network_stats.py` | 从模拟结果中取出需要的数据 |
| `../docker/` | 提供整理好的运行环境和启动脚本 |

项目使用 gem5 和其中的 Garnet 来模拟芯片内部的数据传输。对目前的学习来说，可以先把它们理解为实验工具。Python 程序负责安排实验，模拟工具负责计算传输过程，最后再把结果保存成表格和图片。

### 1. 沿着一次实验阅读代码

以 `rl_QLearning_example.py` 为例，主程序不是一次性给出最终答案，而是有两层循环。外面一层表示重复学习，默认重复 50 轮；里面一层改变发送数据的强度，从 0.05 开始，每次增加 0.05，到 0.60 为止，一轮共 12 种情况。

这里的数字是原项目生成流量的参数，不能直接当作“小程序发送多少个包”。理解时可以先把它看成从比较空闲到比较繁忙的一组条件。

每次循环先选择一种规则，再调用 `icn_routing_gym()`。这个函数会启动外部模拟程序，模拟结束后读取统计数据，再把本次的数据量参数、选择的规则、耗时和轮次一起记录下来。因此，学习程序与模拟程序分工不同：前者决定试什么，后者提供试完之后的反馈。

按默认设置计算，一种学习方法需要大约 50×12＝600 次模拟。这也解释了为什么直接运行完整程序可能需要较长时间。初次学习时，先弄清楚一次调用的输入与输出，比直接等完整结果更容易理解。

### 2. “学习”到底记录了什么

程序中的 Q 表可以先理解成一张经验表：每一行代表一种数据量条件，每一列代表一种路线规则，格子里的数值表示目前对这个选择的评价。

同一个规则在不同数据量下可以有不同评分，因此不能简单地把学习结果理解为“永远选择某一种规则”。更接近项目思路的理解是：在某种条件下，优先选择经验表里评价较好的那个选项。

我还注意到，主脚本使用平均耗时的负数作为评价。例如耗时为 10 时，评价是 -10；耗时为 20 时，评价是 -20。虽然两者都是负数，但 -10 更大，所以选择较大的评分仍然对应更低的耗时。

### 3. 为什么要保留随机尝试

如果程序永远只选当前分数最高的规则，其他规则可能没有得到足够尝试。项目的选择函数会保留一定的随机机会，让程序偶尔试一下别的选项。

对初学者来说，可以把它理解为“多数时候参考经验，少数时候再试试看”。不过，尝试比例是否合适不能只凭直觉判断，所以后面的小实验也加入了这项对照。

### 4. 几个脚本有什么区别

| 程序 | 初步理解 |
| --- | --- |
| `basic_routing.py` | 依次固定使用三种规则，观察各自表现，为比较提供参照 |
| `rl_QLearning_example.py` | 更新经验时，参考下一种条件下目前评价最高的选择 |
| `rl_sarsa_example.py` | 更新经验时，参考下一步实际选中的那个选择 |
| `rl_expected_sarsa_example.py` | 更新经验时，把下一步不同选择的评分按选择概率综合起来 |

这些差别主要在“如何更新经验”，而不是分别使用三个完全不同的模拟工具。目前我主要沿着 Q-learning 脚本阅读，其余两种只做流程上的对照，还没有独立验证它们的效果。

### 5. 结果文件可以怎样看

统计提取程序会从模拟输出中读取平均耗时、接收的数据量和模拟时间等信息。结果表格便于逐项比较，图片便于观察整体变化。

开始时我容易把“奖励越来越大”直接当作“性能一定变好”，后来发现还需要确认实验条件是否一致。例如发送数据量不同，平均耗时本来就可能不同；同样的数据量下也要看是否有足够多的数据成功送达。只看一张曲线，很难判断变化究竟来自路线选择，还是来自实验条件变化。

## 五、根据原理编写的小测试

### 1. 先观察为什么会排队

在选择路线之前，先用已有的 [`learning/01_link_queue.py`](learning/01_link_queue.py) 观察一条连线。它每一步最多传送一个包，分别输入“每一步产生一个包”和“第一步同时产生三个包”。

```bash
python3 commit1/learning/01_link_queue.py
python3 commit1/learning/01_link_queue.py --burst
```

本次运行得到：

| 发送方式 | 三个包分别耗时 | 平均耗时 |
| --- | --- | ---: |
| 分三步各产生一个包 | 1、1、1 步 | 1.00 步 |
| 第一步同时产生三个包 | 1、2、3 步 | 2.00 步 |

两种情况下发送的总数都是三个包，但集中发送会让后面的包等待。这让我意识到，分析传输效果时，除了看总数据量，还要看数据在什么时候到达。总数相同，不代表排队情况相同。

这个练习中没有丢包，也没有复杂的中间节点。等所有包发送完后才计算平均值，因此后面排队较久的包也会计入结果。

### 2. 再加入两条可选择的路线

为了理解“数据量变化后，合适的路线也可能变化”，我另外写了一个小程序：[`learning/simple_route_demo.py`](learning/simple_route_demo.py)。它可以直接使用 Python 3 运行，不需要安装项目的模拟工具。

练习中只设置两条假想路线：

- A 路线比较近，基础传输时间为 1 步，每步最多发送 2 个包。
- B 路线稍远，基础传输时间为 2 步，每步最多发送 5 个包。

假设一批数据包同时准备发送，超过当前发送能力的部分就需要等待。“一步”只是这个小模型的时间单位。这里的 A、B 是自行设定的例子，不代表项目中某种实际规则。

**先计算排队后的平均耗时。** 核心代码如下：

```python
ROUTES = {"A": (1, 2), "B": (2, 5)}

def average_delay(packet_count, route):
    travel_time, capacity = ROUTES[route]
    delays = [travel_time + i // capacity for i in range(packet_count)]
    return sum(delays) / packet_count
```

其中 `i // capacity` 表示这个包需要等待几步。例如 A 每步能发送 2 个包，前两个包不用等待，第三、第四个包需要等待 1 步，再后面的包继续排队。

**再让程序根据耗时积累选择经验。** 开始时两条路线的评分都是 0，每次选择一条路线，用平均耗时的负数作为评价，再调整评分。耗时越小，评价越高。

```python
scores = {"A": 0.0, "B": 0.0}
for _ in range(200):
    if rng.random() < 0.2:
        route = rng.choice(list(ROUTES))
    else:
        route = max(scores, key=scores.get)

    reward = -average_delay(packet_count, route)
    scores[route] += 0.2 * (reward - scores[route])
```

这里 `rng` 是完整程序中使用的随机数工具。程序有 20% 的机会随机尝试，其余时候选择当前评分较高的路线。更新语句的意思是：让旧评分向本次评价靠近一点。每种数据量分别练习 200 次。这只是简化的评分学习，没有实现完整 Q-learning，也没有模拟真实芯片。

在项目根目录运行：

```bash
python3 commit1/learning/simple_route_demo.py
```

实际输出为：

```text
人为设定的路线练习；时间单位为模型中的一步。
同时发送 2 个包：A 平均 1.00 步，B 平均 2.00 步；练习后选择 A
同时发送 20 个包：A 平均 5.50 步，B 平均 3.50 步；练习后选择 B
```

结果让我更容易理解为什么不能只看路线远近。数据少的时候，较近的 A 更快；同时发送的数据变多后，A 的排队时间增加，容量较大的 B 反而更快。简单的评分更新也能逐渐找到这两种情况下更合适的选择。

这些差异来自我预先设定的距离和容量，只能帮助理解排队与选择的关系，不能用于判断项目中三种路由规则的性能，更不能作为论文复现结果。

## 六、补充对照实验与结果分析

只有“两种数据量、两条路线”的结果还比较单薄，因此在原练习的基础上增加了 [`learning/route_experiments.py`](learning/route_experiments.py)。这份程序继续使用简单的耗时计算和评分更新，只改变输入条件，观察结果是否符合预期。

运行命令：

```bash
python3 commit1/learning/route_experiments.py
```

每次运行会在 [`learning/results/`](learning/results/) 保存五份 CSV 表格。下面的数字均来自本次实际运行；表内时间统一使用小模型中的步数。

### 1. 增加数据量后，两条路线有什么变化

保持 A 的容量为 2、B 的容量为 5，逐渐增加同时发送的包数。每种包数都重新建立评分表，练习 200 次后查看选择。

| 同时发送的包数 | A 平均耗时 | B 平均耗时 | 练习后的选择 |
| --- | ---: | ---: | --- |
| 2 | 1.000 | 2.000 | A |
| 4 | 1.500 | 2.000 | A |
| 6 | 2.000 | 2.167 | A |
| 8 | 2.500 | 2.375 | B |
| 10 | 3.000 | 2.500 | B |
| 12 | 3.500 | 2.750 | B |
| 16 | 4.500 | 3.125 | B |
| 20 | 5.500 | 3.500 | B |
| 30 | 8.000 | 4.500 | B |
| 40 | 10.500 | 5.500 | B |

结果中，6 个包时 A 仍稍快，8 个包时 B 开始占优。在这组检查点上，数据量越大，B 的优势总体越明显。这与两条路线的设定一致：A 节省基础传输时间，B 减少大量数据同时到来后的等待。

这里的“8 个包”不是通用分界点，只是当前距离和容量下的结果。更换参数后，分界位置也会改变。另外，这项练习是分别学习每种条件，不是让程序第一次遇到新数据量就自动知道答案。

### 2. 与固定选择、随机选择进行比较

为了判断“根据条件选择”是否有作用，把上面十种数据量看成十个等权重场景，分别计算固定用 A、固定用 B、等概率随机选择和学习后选择的结果。

| 方法 | 十个场景的平均耗时 |
| --- | ---: |
| 始终选择 A | 4.200 |
| 始终选择 B | 3.042 |
| 等概率随机选择的理论平均 | 3.621 |
| 每个场景练习 200 次后选择 | 2.875 |
| 直接比较两条路线、每次选较快者 | 2.875 |

随机一项直接按 A、B 各一半计算，是理论平均值，没有用少量随机抽取来凑结果。最后一项提前知道全部耗时，用来检查学习结果是否选对，而不是另一种学习算法。

本次学习后的选择与直接取较小耗时一致，说明在这种简单、无波动的条件下，评分能找到合适的选项。相比固定 B，改善并不大，因为 B 在多数场景下本来就较快；相比固定 A，差别更明显。这说明评价一种方法时，参照对象的选择会影响结论。

这张表是“先分别学习，再看最终选择”的比较，没有把训练过程中的耗时算进去。每种场景的平均值权重相同，也不是把所有场景的全部数据包合起来求平均。真实使用时还要考虑学习成本，不能把这里的数字直接当成实际系统收益。

### 3. 改变路线容量，选择会不会跟着变

这次固定同时发送 20 个包，A 保持不变，只调整 B 每步最多能发送的包数。B 的基础传输时间一直为 2 步。

| B 每步容量 | A 平均耗时 | B 平均耗时 | 练习后的选择 |
| --- | ---: | ---: | --- |
| 1 | 5.500 | 11.500 | A |
| 2 | 5.500 | 6.500 | A |
| 3 | 5.500 | 4.850 | B |
| 5 | 5.500 | 3.500 | B |
| 8 | 5.500 | 2.800 | B |

当 B 和 A 容量一样时，B 因为基础传输时间更长而处于劣势；当 B 容量提高到 3 后，排队减少带来的好处已经超过多走一步的代价。

这项结果也提醒我：不能预先把 A 理解成“差路线”、B 理解成“好路线”。路线表现取决于条件，学习程序应该根据实际反馈调整判断，而不是记住一个固定名称。

### 4. 练习次数越多，选择是否更可靠

前面的反馈没有波动，比较容易学。为了增加一点不确定性，这次在每次观察到的耗时上加入 -1 到 1 步的随机变化，模拟同一选择每次观察结果不完全相同的情况。这是人为加入的波动，不是真实网络测量。

选择 2、6、10、20 个包四种条件，每种条件使用 50 组不同随机数重复，共 200 次独立练习。改变每次练习的长度，最后关闭随机选路，按评分较高者作决定，再用不加波动的耗时检查它是否选中了较快路线。

| 每个场景的练习次数 | 选中较快路线的比例 | 最终选择的评估平均耗时 |
| --- | ---: | ---: |
| 1 | 50.0% | 2.562 |
| 5 | 69.0% | 2.440 |
| 20 | 82.0% | 2.358 |
| 100 | 91.5% | 2.269 |
| 500 | 95.5% | 2.257 |

在这一组设置中，增加练习次数后，选择较快路线的比例总体提高，平均耗时逐渐下降。四种条件全部选对时的平均耗时为 2.250，本次 500 次练习后的结果已经比较接近。

但练习 500 次仍没有达到每次都选对。一个原因是两条路线有时差别很小，例如 6 个包时只相差约 0.167 步，容易受到随机变化影响。另外，评分更新始终接受一部分新结果，后期也会继续变化，并不是试过足够多次后就完全固定。

所以这里看到的是当前参数下的总体趋势，不能保证每一次增加练习次数都一定改善，也不能把 95.5% 当成项目本身的准确率。

### 5. 随机尝试比例是不是越大越好

保持上一项的四种条件、50 组随机数和耗时波动，每次练习 100 次，只改变随机尝试比例。检查时仍根据最终评分直接选择。

| 练习中的随机尝试比例 | 最终选中较快路线的比例 |
| --- | ---: |
| 0% | 92.5% |
| 10% | 93.0% |
| 20% | 91.5% |
| 50% | 94.5% |
| 100% | 94.5% |

这组结果没有显示“尝试比例越高，结果就一定越好”，也没有证明原练习中使用的 20% 最合适。50% 和 100% 在本次检查中表现相同，其他几项也比较接近，还不足以断言哪一个参数普遍更好。

0% 也能得到比较高的比例，开始看起来有些意外。结合代码可以发现，两条路线初始评分都是 0，第一次选中的路线收到负评价后，另一条尚未尝试的路线仍然是 0，于是也会被选到。因此，0% 随机尝试并不等于整段练习从来只走一条路线。

100% 表示练习时完全随机，但练习结束后仍根据积累的评分选择，并不是评估时也随机走。这项比较只看最后的选择，没有比较练习期间付出的耗时；如果要评价总体效率，还需要把这一部分补上。

## 七、初步分析与不足

我认为这个项目比较容易理解的一点，是它把“尝试—观察—调整”的过程落实到了具体实验中。程序不仅选择规则，还会保存耗时等结果，方便之后比较。项目也提供了多种学习方法，可以在熟悉基本流程后继续了解。

目前接触下来，主要困难是环境和文件较多。部分原始脚本中写着作者电脑上的固定路径，换一台机器时不能直接照搬。仓库提供的 Docker 配置有助于整理运行环境，但初学者仍然需要先弄清楚从哪个入口启动。

另外，现有的短时间验证主要说明程序可以运行，还不足以判断长期学习效果。如果后续继续做，我会先比较三种固定规则在不同数据量下的表现，再观察学习程序是否能选到更合适的规则。这样更容易看清学习方法带来的实际变化。

阅读和小实验中还整理了几个具体问题：

| 遇到的问题 | 目前的处理或理解 |
| --- | --- |
| 原始代码较多，不知道从哪里开始 | 先跟随一次“选规则—启动模拟—读取结果—更新评分”的调用，再回头看其他文件 |
| 负数奖励看起来不直观 | 用 -10 和 -20 比较，确认耗时越小，对应评价越高 |
| 一开始的结果只有两行，难判断变化 | 增加多组数据量，并与固定选择进行对照 |
| 随机运行的结果可能变化 | 固定随机数用于重复观察，再换 50 组随机数检查结果是否稳定 |
| 学习次数多时结果仍不完全正确 | 检查两条路线差距、观测波动和评分更新方式，不直接认定程序出错 |
| 更换参数后结论变化 | 保持其他条件不变，一次只改变一项，并分别保存结果 |

对于原项目，还需要注意模拟进程是否成功退出，以及读到的统计是否属于刚完成的这次实验。阅读接口代码时可以看到，它启动命令后继续读取文件，如果缺少运行状态检查，理解结果时就应特别核对文件来源。本次小练习直接计算耗时，避开了外部环境问题，但也因此不能替代真实模拟。

小模型还有明显简化：一整批包使用同一条路线，没有同时分流；每次尝试都从空队列开始，没有跨批次积压；不考虑丢包、有限等待空间以及多个节点之间相互影响。它适合解释“等待影响耗时”和“反馈影响选择”，与完整芯片网络还相差很远。

为了回顾这次学习，把实际涉及的内容按先后关系整理如下。这里记录学习阶段和可检查的产物，不把它当作已经完成的逐日实验日志。

| 阶段 | 主要内容 | 可以检查的产物 |
| --- | --- | --- |
| 背景了解 | 理解核心通信、数据排队和选路的关系 | 报告第一、二节 |

| 独立练习 | 自行设定两条路线，实现耗时计算和评分更新 | `simple_route_demo.py` |

补充实验的结果文件分别为：

- [`load_comparison.csv`](learning/results/load_comparison.csv)：不同数据量下的路线耗时和学习选择。
- [`strategy_comparison.csv`](learning/results/strategy_comparison.csv)：固定、随机和学习后选择的对照。

## 九、学习体会与后续方向

通过这次初步阅读，我对项目的认识从“用人工智能优化芯片”变得具体了一些：它主要是借助模拟实验，在几种已有的数据传输规则中学习如何选择。

目前我能够理解项目的大致目标、主要运行流程和结果文件的作用。通过排队观察和几组小实验，也初步看到了数据量、容量、等待时间和路线选择之间的关系，但对完整学习方法内部的计算过程还需要进一步了解。

这次学习比较有帮助的一点，是把“运行成功”和“方法有效”分开理解。程序能输出结果，只是说明流程可以完成；是否更好，还需要有固定方法作为参照，需要保持条件一致，也需要多运行几次查看结果是否容易变化。

下一步想先完善简单模型，而不是马上堆更多算法。可以把连续到来的数据保留在队列中，观察前一次传输对下一次的影响；也可以在练习过程中突然改变一条路线的容量，看看已有经验能否及时调整。等这些现象能够解释清楚后，再去阅读完整 Q-learning 的更新过程，并尝试对应到原项目的一次小规模模拟。
